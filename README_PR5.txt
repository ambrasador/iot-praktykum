  Результат — каталог pr05/ (calc.mjs, adr-005.md для рівня «5»), змінені greenhouse-monitor/push.js

остаточні версії з каталогу greenhouse-monitor; лістинги розділу показують, як файл виглядав у підручнику.
  push.js                розділ 5
  push.test.js           розділ 5

Файли, яких немає в еталонному застосунку, ви створюєте самі: calc.mjs, adr-005.md.

Підручник: робота спирається на п. 5.1.2, 5.3, 5.4.2–5.4.4, 5.5.2 і 5.9 підручника. Код розділу 5 — у підручнику й у репозиторії greenhouse-monitor.

5. ЯК ЗАПУСТИТИ
====================================================================================================
Журнал track.json і каталоги pr01…pr08 уже створено в ПР1. Вхідний контроль ПР5 починається з
перевірки журналу ПР4: помилка в попередній роботі показується тут.

Команди інструментів, як їх наведено в тексті роботи (підрозділ 5.4; повні параметри — там):
  node kit/tools/noise.mjs
  node kit/tools/qinv.mjs --n 1440 --r 1
  node kit/tools/push-replay.mjs
  node kit/tools/push-replay.mjs --sweep
  node kit/tools/push-replay.mjs --h 2
  node kit/tools/push-sample.mjs
  node kit/tools/push-sample.mjs --ttl
  node kit/tools/push-sample.mjs --ttl --max-age 700
  node kit/tools/push-sample.mjs --json
  node kit/tools/queue-sim.mjs

Контроль:
  node kit/tools/verify.mjs pr05                    рівень, заявлений при init
  node kit/tools/verify.mjs pr05 --level 4          показати, скільки лишилося до рівня «4» (або 5)
  node kit/tools/verify.mjs pr05 --declared-only    пропустити довідкові блоки рівнів вище заявленого
Числа в журнал вносять командою node kit/tools/track.mjs set <ключ> <значення>; node kit/tools/track.mjs show друкує журнал.

6. ЩО ПЕРЕВІРЯЄ verify.mjs pr05
====================================================================================================
Пункти, які контроль друкує на демонстраційному варіанті 0 при рівні «5»; ✓ — пункт виконано. У
вашому варіанті формулювання збігаються, а очікувані числа свої.

Рівень «3» — 6 пунктів
  ✓ Вхідний контроль: ПР3 (канал) і ПР4 (k і період опитування карток) виконано
  ✓ BLE і прив’язка: записів у характеристику (формула 5.3), строк очікування онлайну (формула 5.4)
    і режим прив’язки
  ✓ Годинник телефона: похибка оцінки (формула 5.2), запас до хибного «Немає даних», вердикт зсуву,
    період опитування мобільного клієнта
  ✓ Шум датчика метрики сповіщення: σ на всьому ряді й на спокійній ділянці, множник k для
    допустимих повторів, гістерезис h (формули 5.6 і 5.8)
  ✓ push.js: карта RULES_<код> із правилами карток домену; тести зелені й ловлять зміну порога
    (мутації warn + 1, crit + 1)
  ✓ Правила під навантаженням: шум біля порога тривоги, спад і повернення до норми — через
    createAlertTracker із вашими правилами

Рівень «4» — 3 пункти
  ✓ Повідомлення за правилами домену: значення з decimals метрики, одиниця, заголовок; диспетчер
    приймає rules, імітація FCM не знаходить порушень
  ✓ Строк актуальності й розмір: PUSH_<код> у push.js (TTL, найбільший вік події не більший за TTL),
    тест на цю умову, байти повідомлення
  ✓ Черга дій: повтори при втраті відповіді — рядки без ключа, з ключем на спробу й на дію, теорія
    (формула 5.7)

Рівень «5» — 2 пункти
  ✓ Повтори FCM у межах TTL: скільки пауз вміщається при 503 і 429 (найбільший і найменший джитер),
    чим закінчується постійна відмова
  ✓ ADR-005 (мобільний клієнт домену): гістерезис, TTL і вік події, період опитування, режим
    прив’язки, ключ ідемпотентності, тригер перегляду

Оцінка дорівнює найвищому рівню, всі пункти якого виконано (і всіх нижчих). Опис рівнів і складу
звіту — у підрозділах 5.5 і 5.6 практикуму; повні тексти завдань — у додатку Б.
